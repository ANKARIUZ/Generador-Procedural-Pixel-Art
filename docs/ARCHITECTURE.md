# Technical Architecture — Procedural City Engine

## 1. Architecture Overview

Procedural City Engine will use a modular architecture developed in Rust.

The system must separate procedural generation, geometry, materials, rendering, camera control, simulation, and application management.

Each module should have a clearly defined responsibility.

The architecture must allow individual systems to evolve without requiring unnecessary modifications to unrelated modules.

## 2. Technology Stack

| Technology | Responsibility |
|---|---|
| Rust | Main programming language |
| Cargo | Dependency and project management |
| wgpu | GPU rendering API |
| winit | Window creation and input events |
| glam | Mathematical operations and transformations |
| bytemuck | GPU-compatible data conversion |
| png | Codificación PNG de sprites |
| serde / serde_json | Esquema versionado y lectura/escritura JSON |
| rand | Random generation |
| rand_chacha | Reproducible random generation |
| rayon | Parallel processing when required |

No external game engine will be used.

## 3. Main Modules

### 3.1 Core

Contains shared structures and fundamental utilities.

Responsibilities:

- Global configuration.
- Mathematical utilities.
- Shared types.
- Common application structures.

### 3.2 Geometry

Responsible for representing and generating geometric objects.

Core structures:

- Vertex.
- Face.
- Mesh.
- Primitive.
- Transform.

Geometry must not depend on the rendering system.

A mesh should represent vertices, indices, and geometric information independently of the GPU.

The geometry system must support triangles and quadrilaterals, allowing complex shapes such as inclined roofs.

### 3.3 Procedural Generation

Responsible for creating objects using algorithms and configurable parameters.

Examples:

- Houses.
- Buildings.
- Trees.
- Roads.
- Urban objects.

Generation must support deterministic seeds.

The procedural system should produce geometry and object data without directly rendering anything.

### 3.4 Materials

Responsible for defining the visual properties of surfaces.

A material may contain:

- Base color.
- Surface properties.
- Texture references.
- Lighting parameters.
- Transparency settings when needed.

Different faces of the same mesh may use different materials.

### 3.5 Rendering

Responsible for transforming geometric data into pixels.

This module will use wgpu.

Responsibilities:

- GPU initialization.
- Render pipelines.
- Shader management.
- Vertex and index buffers.
- Depth buffering.
- Material application.
- Lighting.
- Shadows.
- Pixel Art rendering.

Rendering must consume geometry generated by other modules.

It must not be responsible for deciding how buildings are procedurally constructed.

### 3.6 Camera

Responsible for view and projection transformations.

Initial requirements:

- Orthographic projection.
- Diagonal camera position.
- Zoom.
- Rotation.
- Camera movement.

The camera must remain independent of procedural generation.

### 3.7 Application

Responsible for the application lifecycle.

Responsibilities:

- Window management.
- Input events.
- Application initialization.
- Update loop.
- Rendering loop.
- User interaction.

### 3.8 Simulation

This module belongs primarily to the future game and will be introduced only when required. The asset generator may define damage states without implementing a complete world simulation.

It will manage the state and behavior of the simulated world.

Examples:

- Fire.
- Smoke.
- Damage.
- Destruction.
- Population.
- Vehicles.
- Economy.
- Environmental conditions.

Simulation updates must not depend on whether an object is currently visible on screen.

### 3.9 Diagnóstico opcional

El módulo `diagnostics`, habilitado exclusivamente mediante la característica de
Cargo homónima, observa presentaciones exitosas que comunica la capa de
aplicación. Su dependencia es unidireccional: el diagnóstico consume eventos y
métricas del motor, pero `geometry` y `render` no conocen su implementación.
No modifica cámara, geometría, simulación ni recursos de GPU; solo calcula una
instantánea ligera y la aplicación puede mostrarla en el título de la ventana.

### 3.10 Escena

`scene` es una capa CPU sin dependencias de winit ni wgpu. `Scene` posee las
`Mesh` registradas y conserva instancias `SceneObject` que las referencian por
`MeshId`; cada instancia tiene un `ObjectId` monotónico, una `Transform` validada
y un estado de visibilidad. La malla no se copia en los objetos.

`Transform` usa traslación en unidades de mundo, rotación normalizada y escalas
positivas. Su matriz de modelo sigue `Translation × Rotation × Scale`. El
renderizador consume esa matriz junto con la vista-proyección de la cámara, sin
alterar coordenadas locales de `geometry`.

## 3.11 Modelo de edificios procedurales (diseño futuro)

El propósito principal de Procedural City Engine es **generar assets urbanos pixel art** reproducibles y exportables. La ventana, la cámara y la escena son herramientas de inspección, no un motor de videojuego completo.

Se adopta un **modelo híbrido** con responsabilidades separadas:

1. **Modelo arquitectónico:** componentes identificables (paredes, cubierta, puertas, ventanas, columnas y pisos), dimensiones, materiales y relaciones. Su identidad es independiente de las mallas y de los recursos GPU.
2. **Estado de daño:** deterioro progresivo y localizado por componente o región. Se implementará primero el daño visual; las relaciones de soporte y los colapsos se contemplarán en el diseño, pero se implementarán después.
3. **Representación visual:** generación de superficies geométricas optimizadas y subdivisión local en fragmentos o vóxeles solo donde aporte detalle. El renderizador consume el resultado, sin decidir reglas arquitectónicas ni de daño.

El generador podrá producir variantes deterministas mediante semilla, parámetros y versión del algoritmo. Se distinguirán propiedades **visuales** del material (paleta, color, acabado) de propiedades **de comportamiento futuro** (combustibilidad, resistencia y respuesta al daño); definirlas no implica simular incendios ahora.

La exportación futura incluirá imágenes pixel art y, cuando corresponda, datos estructurales, identificadores y metadatos de materiales/daño. El juego futuro será responsable de decidir eventos y simular propagación, física, economía y tráfico.

**Reglas:** `building` y `damage` son módulos previstos, no deben crearse hasta el sprint correspondiente; no imponer una cuadrícula voxel densa a todo el edificio; no introducir dependencias de wgpu en el modelo arquitectónico; medir antes de optimizar; preservar compatibilidad con `Scene` y la característica opcional `diagnostics`.

### 3.11 Modelo de edificio

El módulo `building` reutiliza `scene::Transform` mediante una dependencia
unidireccional. El modelo funciona sin una instancia `Scene` y sin dependencias
de `geometry`, wgpu o winit. `Building` posee componentes con identidad estable,
dimensiones, transformación y una referencia tipada de material.
Las relaciones de pertenencia se validan según el tipo arquitectónico:
puertas y ventanas se enlazan a paredes; techos a paredes o columnas; y pisos,
paredes y columnas a soportes compatibles.

`BuildingId` identifica una instancia en el proceso. `Building::new()` lo asigna
mediante un contador atómico de 64 bits y devuelve `BuildingIdExhausted` antes de
que el contador desborde. La asignación es segura entre hilos y los IDs se
conservan reservados al destruir instancias. `Building` carece de `Clone` y
`Default`. Mover o compartir una instancia conserva su identidad.

`ComponentId` es monotónico y local. `ComponentRef` combina ambos IDs con
construcción interna. Toda operación pública que resuelve un componente exige
esa referencia y devuelve `ForeignComponent` si procede de otro edificio,
incluso si el ID local coincide.

Las identidades de instancia tienen alcance de proceso y pueden repetirse tras
reiniciar o entre procesos. Una futura deserialización deberá crear instancias
con IDs nuevos y reconstruir referencias a partir de datos persistentes. En el
Sprint 6, la reproducibilidad se evaluará sobre datos, orden e IDs locales,
independientemente del orden de asignación de identidades de instancia.

El modelo no genera mallas, no construye una casa aleatoria y no simula soporte,
combustión o destrucción. Es la entrada estructural que un generador posterior
convertirá explícitamente en geometría y objetos de escena.

### 3.12 Generador estructural de viviendas

`procedural::generate_house(&HouseConfig)` valida la configuración y la
capacidad de aberturas antes de crear una instancia `Building`. Usa las
referencias compuestas y las operaciones públicas de `building`, junto con
`glam` y `scene::Transform`. La demostración de consola inspecciona el resultado
mediante `cargo run --example house`.

`HouseConfig` controla ancho, profundidad, altura de pared, desnivel del techo,
dimensiones de puerta y ventana, cantidad de ventanas, semilla y referencias
`HouseMaterials`. Las dimensiones de entrada están en unidades de mundo y
deben estar entre 0.001 y 1024, inclusive. Las reglas de planta y aberturas
imponen mínimos adicionales. La fundación mide 0.30 de espesor, el piso 0.15,
las paredes 0.20 y cada agua 0.12.

La vivienda usa coordenadas de mano derecha y un origen en el centro inferior
de la fundación. X mide el ancho, Y crece hacia arriba y +Z apunta a la fachada.
Las paredes frontales y traseras ocupan todo el ancho. Las laterales llegan
hasta sus caras interiores. El piso pertenece a la fundación, las cuatro
paredes al piso y cada abertura a su pared.

La puerta queda centrada en la fachada y apoyada sobre el piso. Las ventanas
se reparten entre la pared trasera y las dos laterales. Se reservan 0.25 en
cada extremo de pared, 0.20 arriba, 0.30 entre ventanas y 0.65 de antepecho
desde el piso. La puerta utiliza los mismos márgenes de extremos y coronación.
Un recuento de cero ventanas es válido. Puertas y ventanas describen aberturas
conceptuales que una conversión posterior podrá usar para generar paños de
pared alrededor de los huecos.

Las dos aguas son componentes `Roof` inclinados alrededor de Z. Sus planos
medios se encuentran en una cumbrera paralela a Z, sobre X = 0. La pendiente
angular se calcula como `atan2(roof_rise, width/2)`. Cada agua pertenece a su
pared lateral. La representación tiene espesor conceptual y carece de
aleros, hastiales, mallas y remates de unión.

La versión 1 usa SplitMix64 local con semilla explícita para barajar el orden
de asignación de ventanas y desplazar cada grupo dentro de su holgura. Las
pruebas comparan tipos, dimensiones, transformaciones, materiales y relaciones
por ID local, excluyendo la identidad de instancia. La reproducibilidad
corresponde a la misma versión y plataforma. Las funciones trigonométricas
pueden introducir diferencias de redondeo entre plataformas.

### 3.13 Perfil geométrico de cubierta

`geometry::roof::RoofProfile` calcula secciones y extremos 3D con `glam`.
`procedural::derive_house_roof` adapta la planta, coronación, pendiente y
espesores del `Building` generado. Comprueba paredes y apoyos compatibles.
La representación estructural de la versión 1 conserva sus dos aguas
originales y sus relaciones.

El perfil XY está en el marco de la vivienda, con la cumbrera en X = 0 y
extrusión paralela a Z. Dados el semiancho `r`, el desnivel `h`, la cota de
pared `y0` y el espesor normal `t`, la cara inferior cumple
`y = y0 + h * (1 - abs(x)/r)`. La cara superior se desplaza verticalmente
`t * hypot(r,h)/r` para mantener la distancia normal `t`. Esto conserva
la pendiente del modelo estructural y hace que su cota de cumbrera nominal
pase a ser la cota inferior. Ambas caras se limitan por cortes verticales
en X = 0 y X = ±r. Los extremos longitudinales son Z = ±profundidad/2.
Los cortes quedan a ras de las fachadas con vuelo cero.

Los hastiales triangulares ocupan el espesor de las paredes frontal y
trasera. Los rellenos triangulares de coronación ocupan el espesor de las
paredes laterales entre los hastiales. Todos empiezan en `y0` y terminan en
la cara inferior. Compartir límites permite el contacto geométrico con
interiores disjuntos. El futuro mallador deberá suprimir la cara interna
de la unión de cumbrera y recortar o subdividir las interfaces compartidas
entre cubierta, paredes y rellenos para emitir solo la frontera exterior.
Las secciones aún carecen de índices, triangulación y garantía de malla
cerrada o manifold.

El adaptador usa hasta ocho épsilon de `f32` escalados por la magnitud
pertinente para reconciliar los datos estructurales. El perfil opera en
`f64` y rechaza separaciones menores o iguales a 16 épsilon de `f64`
multiplicados por la escala de la envolvente. En pendientes próximas a la
vertical, la separación vertical puede superar ampliamente el espesor
normal. `cargo run --example roof` muestra aristas y secciones.

### 3.14 Mallado de viviendas

`meshing::mesh_building(&Building)` devuelve una `BuildingMesh` con una malla
indexada, un `ComponentRef` por triángulo y el rango de caras de la envolvente.
El mallador consume la disposición de una planta de `generate_house` y el
`RoofProfile` del Sprint 6.1 mediante el adaptador procedural. Mantiene el marco
de la casa y los materiales originales.

Los huecos se proyectan al marco local de sus paredes. Sus rectángulos dividen
la planta en franjas Z y cada franja en intervalos X. Las bandas sólidas
describen fundación, piso, paredes, hastiales, rellenos laterales y cubierta.
En cada frontera se emite la parte que separa espacio sólido de espacio libre,
incluidas jambas, dinteles y alféizares. El mismo criterio omite las interfaces
entre piso y paredes, entre apoyos y cubierta y en la junta de cumbrera. Las
caras superiores e inferiores siguen los niveles inclinados de `RoofProfile`.

Las aristas colineales se subdividen en los puntos compartidos antes de
triangular polígonos convexos. Las posiciones representables coincidentes
comparten un índice. La puerta y cada vidrio opaco se emiten como sólidos
independientes, centrados en su hueco, con la mitad del espesor de pared y una
holgura del 2 % por borde de ancho y alto.

La validación comprueba posiciones, índices, áreas, triángulos duplicados y
dos incidencias opuestas por arista geométrica. Esa comprobación no certifica
ausencia de autointersecciones arbitrarias ni la vecindad de cada vértice.
El adaptador rechaza disposiciones incompatibles con la planta admitida.

La variable `PCE_SCENE=house` selecciona la vivienda. La aplicación registra
una sola malla y usa una paleta con los seis IDs materiales predeterminados.
La conversión CPU conserva otros IDs, cuya visualización requiere una paleta
que los resuelva.

### 3.15 Presentación pixel art isométrica

`App` selecciona `PCE_RENDER_MODE=classic` (predeterminado) o `pixel`.
Ambos modos consumen la misma malla producida por `mesh_building` y la misma
escena. En modo clásico, el pase 3D dibuja directamente a la superficie.
En modo pixel art, el pase 3D dibuja en `Rgba8UnormSrgb` con profundidad
`Depth24Plus` de igual tamaño, culling trasero y una muestra por píxel. Un
segundo pase GPU presenta ese color con `upscale.wgsl`, un triángulo y un
sampler nearest. La presentación habitual ocurre enteramente en GPU.

`PCE_PIXEL_SCALE` acepta enteros de 1 a 8 en modo pixel, con 3 por defecto.
La resolución interna resulta de dividir cada dimensión física por la escala
efectiva y redondear hacia abajo. Cada téxel ocupa un cuadrado de ese factor
en el viewport centrado. Los píxeles físicos restantes forman bandas negras
de relleno, con menos de un bloque de sobrante por eje. La cámara usa la
proporción del viewport interno. El escalado fraccional prolongaría unos
téxeles más que otros, incluso con nearest. Ajustar cada eje a toda la ventana
podría además deformar la proporción. Con la política entera, un área
positiva demasiado pequeña reduce el factor para conservar al menos 1 × 1.
Con una dimensión cero se omite la presentación. Un tamaño válido vuelve
a habilitar el redibujado a través del evento de redimensionamiento.

Los recursos de color, profundidad y el grupo de textura se recrean si
cambian las dimensiones internas. Los buffers de malla, el sampler y los
pipelines se reutilizan. El costo adicional es una textura de color interna
y un pase de presentación a resolución de ventana. Con escala 3, el primer
pase tiene aproximadamente un noveno de los píxeles. La aplicación sigue
redibujando bajo demanda y los diagnósticos cuentan las presentaciones.

La casa arranca en ortográfica con azimut 45° y elevación 35,264° en ambos
modos. Arrastrar con botón izquierdo orbita, la rueda ajusta el zoom,
arrastrar con botón central desplaza, WASD mueve, `R` recupera la vista
inicial y Escape cierra. El zoom altera la proyección de la escena. El
escalado entero estabiliza el tamaño de los bloques en pantalla. En
navegación libre, contornos diagonales y detalles finos aún pueden cambiar
de cobertura al orbitar, desplazar o hacer zoom. Un eventual modo de captura
podría ajustar la traslación en el plano de vista con orientación, escala y
resolución fijas. El sprint conserva la navegación libre sin ese ajuste.

`FacePalette` resuelve seis IDs a RGB lineal, con crema para muros,
terracota para cubierta, gris para fundación, marrón para puerta y azul para
ventanas. El fragmento pixel art obtiene la normal de la cara mediante
derivadas de la posición mundial. Una dirección fija gradúa la luz en
tres factores lineales (0,58 ambiental, 0,78 medio tono, 1,00 iluminado),
con umbrales de producto escalar 0,15 y 0,60. Los tonos dependen de la
orientación mundial de las caras, de modo que la cámara puede cambiar de
posición sin mover la iluminación.

### 3.16 Importación y exportación de viviendas

`asset::HouseAsset` guarda juntos un edificio validado, su malla y el
`AssetManifest`. `generate` crea la vivienda una vez y `from_building`
acepta una vivienda existente con su receta de procedencia. `import_json` toma
como fuente de verdad los componentes y vuelve a mallarlos. Ambos caminos
comparten la malla entre los límites del manifiesto y la exportación de
la imagen. El modelo `Building` sigue independiente de los formatos y GPU.

`asset.json` usa el esquema 1. `kind` identifica la vivienda y `name`
es un nombre lógico controlado, con unicidad a cargo del catálogo que
consuma el paquete. `seed` es un entero `u64` exacto, por lo que un
consumidor debe evitar convertirlo a un número IEEE 754 de doble precisión.
`recipe` incluye medidas, cantidad de ventanas e IDs materiales por rol.
`bounds` registra los extremos XYZ de la malla. Los componentes tienen ID
documental `u32`, tipo, padre opcional, dimensiones, traslación XYZ, rotación
unitaria XYZW, escala XYZ y material. Una instancia importada tiene un
`BuildingId` nuevo. Durante la importación se construye la tabla de ID
documental a `ComponentRef` y se registran las relaciones en una segunda
pasada mediante `Building::attach`. Los valores `f32` usan su representación
decimal de ida y vuelta, con validación de las rotaciones unitarias.

`algorithm_version` identifica la receta. `AssetManifest::regenerate`
ejecuta el algoritmo disponible para esa versión. La importación estructural
también admite otras versiones positivas del algoritmo si el esquema y la
geometría son compatibles. Los componentes se ordenan por ID antes de
reconstruir o reemitir el documento. El esquema 1 limita el JSON a 256 KiB,
los componentes a 128 y el nombre a 64 caracteres ASCII permitidos.
Solo se admite `sprite.png` como referencia relativa. La importación no
abre ese archivo y los errores conservan su causa de E/S, esquema,
estructura, mallado o GPU según la operación.

`visual` fija la orientación isométrica, azimut, elevación, la paleta
RGB lineal y el perfil de iluminación `pixel_v1`. Registra resolución
lógica, factor entero, margen y resolución final. Cada eje final admite
hasta 2048 píxeles y el factor está entre 1 y 8. El margen se mide en
téxeles lógicos. La resolución final resulta de multiplicar cada eje lógico
por el factor. El encuadre proyecta los vértices a los ejes de cámara,
centra su rectángulo y usa una misma escala en ambos ejes. En formatos
rectangulares, el eje sobrante añade espacio transparente.

`render::render_sprite` usa el mismo shader pixel art y formato de
profundidad de la ventana. Dibuja directamente a una textura sRGB lógica
con alfa cero de fondo y uno de geometría. La copia espera a GPU y retira
el relleno de filas exigido por wgpu. El PNG usa alfa recto y la ampliación
entera replica los téxeles durante la escritura. El renderizado offscreen
no requiere ventana, superficie ni swapchain. La reproducibilidad visual
se verifica en el mismo adaptador y controlador.

`export_package` reserva un directorio nuevo, escribe el PNG y publica
`asset.json` al final mediante renombrado de un archivo temporal. Si se
interrumpe el proceso, la ausencia del manifiesto indica un paquete
incompleto. Un directorio existente se rechaza.

## 5. Data Flow

The expected flow is:

```text
Procedural Generator
        |
        v
   Geometry Data
        |
        v
     Materials
        |
        v
     Renderer
        |
        v
      GPU
        |
        v
   Final Image
```

The simulation system will eventually update object states independently.

The renderer will receive the resulting data and display the appropriate visual representation.

## 6. Geometry Principles

Objects must be represented through actual geometric data.

The initial implementation will use modular meshes and geometric primitives.

The system must not be restricted to cubes or six-sided objects.

Complex objects must be possible through combinations of vertices, triangles, and polygonal surfaces.

Visibility must be handled by the rendering pipeline using techniques such as depth testing, back-face culling, and frustum culling where appropriate.

### Convenciones geométricas (Sprint 1)

- Se usa un sistema de coordenadas de mano derecha: X positivo hacia la derecha,
  Y positivo hacia arriba y Z positivo hacia delante.
- Las medidas están expresadas en unidades de mundo sin una escala física fijada aún.
- La representación fundamental de una superficie es el triángulo indexado.
  Un cuadrilátero se triangula en dos triángulos que comparten vértices.
- El orden de los índices es antihorario visto desde el exterior; por tanto, la
  normal geométrica exterior se calcula con `(b - a).cross(c - a)`.
- Las normales no se almacenan en la geometría base: se pueden derivar de la
  posición y topología cuando un consumidor las necesite.
- `Mesh::face_normal` devuelve `Result<Vec3, GeometryError>` para comunicar
  corrupción posterior de la malla sin producir un `panic`.
- `Mesh::add_quad` acepta únicamente cuadriláteros simples, coplanares y
  estrictamente convexos, con índices en el orden del perímetro. Rechaza de
  forma atómica entradas cóncavas, autointersectadas, no coplanares o degeneradas.
- La validación de área calcula productos cruzados en `f64`. No aplica un umbral
  absoluto de área; por ello no descarta triángulos pequeños que sean válidos.
  La coplanaridad usa un margen relativo al tamaño del cuadrilátero para cubrir
  exclusivamente el redondeo numérico.

## 7. Rendering Principles

The rendering system will use a custom pipeline based on wgpu.

The initial rendering approach will prioritize:

- Simplicity.
- Correct geometry.
- Depth management.
- Independent face colors.
- Camera transformations.

### Contrato de renderizado inicial (Sprint 2)

- El módulo `render` consume `geometry`, pero la geometría no depende de wgpu,
  WGSL ni recursos de GPU.
- Para resolver materiales por cara en mallas con vértices compartidos, los datos
  de GPU expanden cada triángulo en tres `GpuVertex`. Los buffers se crean una
  vez durante la inicialización y no se regeneran por fotograma.
- La cámara de demostración es ortográfica, diagonal y fija. Usa la proyección
  de profundidad 0..1 compatible con wgpu y actualiza solo el uniform al cambiar
  la relación de aspecto.
- La pipeline usa front face CCW, culling trasero y profundidad `Depth24Plus`;
  los recursos dependientes del tamaño de superficie se recrean al redimensionar.

### Cámara interactiva (Sprint 3)

- `Camera` contiene exclusivamente el estado orbital y las matrices ortográficas;
  no conoce winit, wgpu ni la ventana.
- `CameraController` traduce entradas abstractas de ratón y teclado a cambios de
  cámara. La aplicación es la única capa que conoce los eventos de winit.
- `RenderContext` actualiza el uniform de cámara tras un cambio, sin reconstruir
  los recursos geométricos estáticos. Las actualizaciones continuas se limitan a
  teclado mantenido y el estado inactivo conserva el renderizado bajo demanda.

### Escena e instancias (Sprint 4)

- El renderizador prepara una vez un `GpuMesh` por cada `MeshId` de la escena;
  las instancias que comparten malla comparten sus buffers de vértices e índices.
- Un buffer uniforme de matrices de modelo, alineado según los límites del
  dispositivo, usa offsets dinámicos para seleccionar una matriz distinta por
  draw dentro de la misma submission. Así ninguna instancia recibe la última
  matriz escrita por error.
- Solo los objetos visibles producen draws. Los buffers de geometría, la pipeline,
  la cámara y la profundidad no se reconstruyen por fotograma.
- La demostración se sincroniza explícitamente al inicializar `RenderContext`.
  Añadir mallas u objetos fuera de la capacidad inicial requiere una futura ruta
  explícita de resincronización; el renderizador informa un error en lugar de
  usar recursos GPU desactualizados.

- El renderizador distingue `Presented` de `Skipped` cuando la superficie tiene
  una dimensión cero. Solo `Presented` actualiza el diagnóstico y el límite de
  prueba, y la aplicación vuelve a solicitar dibujo al recuperar un tamaño válido.

Pixel Art effects will be introduced after the basic rendering pipeline is working.

## 8. Architectural Rules

1. Procedural generation must remain independent of rendering.
2. Geometry must not depend on GPU-specific structures.
3. Materials must be reusable.
4. Camera logic must remain independent.
5. Simulation must not depend on visual effects.
6. Avoid unnecessary dependencies.
7. Avoid premature optimization.
8. Introduce new modules only when required.
9. Preserve existing working functionality.
10. Document important architectural changes.
